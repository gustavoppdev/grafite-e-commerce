# Authorization is enforced where data is read and written, not in proxy.ts

`proxy.ts` (formerly `middleware.ts`) redirects Visitors without a session cookie away from protected routes, but only as a convenience: it checks that the cookie exists, never its validity or the role. Every page, server action and data query that touches protected data checks the session and role again itself (e.g. `requireUser()` / `requireAdmin()`) and scopes queries to the owner (a Customer only ever loads their own Orders, Cart and Addresses). This duplication is deliberate: the proxy can be bypassed (see CVE-2025-29927) and does not run for every code path, so it must never be the only line of defense.

Because the proxy cannot tell a valid cookie from a stale or forged one, it must never redirect *away from the sign-in page* based on cookie presence: an invalid cookie would bounce between `/entrar` (proxy: "has a cookie, go to the account") and `/conta` (page: "no valid session, go sign in") until the browser gives up, locking the person out of sign-in (found in auth-core ticket 12). Redirecting signed-in people away from `/entrar` is the page's job, with the session validated against the database.
